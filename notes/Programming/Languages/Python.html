Namespace

A namespace is a mapping from names to objects. It serves as a container for identifiers (variable names, function names, class names, etc.) and helps in avoiding naming conflicts and organizing code logically.

Local Namespace:

  • A local namespace contains the names that are defined within a specific function or method.
  • It is created when a function is called and is destroyed when the function exits.
  • The local namespace is accessible only within the function or method where it is defined.

Enclosing Namespace (non-local):

  • An enclosing namespace contains names defined in the enclosing function or outer scope.
  • It is used in nested functions or closures. use keyword non-local
  • Names in the enclosing namespace are accessible within the nested function but not modifiable by it.

Global Namespace:

  • The global namespace contains names defined at the top level of a module or script.
  • It is created when the module is imported or when the script is executed.

Built-in Namespace:

  • The built-in namespace contains names of built-in functions, exceptions, and other objects provided by Python.
  • It is automatically loaded when Python starts up.
  • The objects in __builtins__ include commonly used functions like print(), len(), range(), etc
  • Python 3, __builtins__ is read-only by default.

Generators

Generators are functions that can pause and resume their execution. They generate a sequence of values lazily, one value at a time, and only when requested.

Memory Efficiency: Generators produce values on-the-fly, so they don’t store the entire sequence in memory at once. This makes them memory efficient, particularly for large datasets.

Lazy Evaluation: Values are generated only when requested, which can improve performance and reduce unnecessary computation.

Support for Infinite Sequences: Generators can produce infinite sequences of values without running out of memory or crashing the program.

Packages

A package is a collection of Python modules organized in a directory hierarchy. It typically contains an __init__.py file to indicate that the directory should be treated as a package. Packages allow you to further organize your code into meaningful units.

Python’s Import System:

In Python, when you try to import a module or a package, Python needs to know where to find it. The location of the module is determined by the sys.path list, which includes directories where Python will look for modules.

What is a Package?

A package is essentially a directory that contains a special file called __init__.py, and it may contain other Python files or subdirectories (which can also be packages). The __init__.py file makes the directory recognizable as a package, allowing Python to treat it as part of the module namespace.

Python’s Default Import Behavior

When you attempt to import a module in Python (e.g., import path), Python looks for it in the directories listed in sys.path. By default, sys.path includes:

  • The directory of the script you’re running
  • The directories in the PYTHONPATH environment variable
  • The standard library directories

However, if path is not in the same directory as working, so Python doesn’t know where to find it unless you explicitly tell it to.

When you run Python with the -m flag (e.g., python -m server.controller), you’re running the module server.controller as part of the package structure starting from the root directory (which must be in sys.path).

This is important because relative imports and absolute imports work only if Python knows how to locate your modules within the correct package structure.

pycache

__pycache__ is a directory automatically created by Python when it compiles source files into bytecode files. Python compiles source files into bytecode (.pyc) files to speed up execution by avoiding recompilation each time the script is run.

  1. When you import a module in Python, the interpreter first checks if there’s a corresponding bytecode file (.pyc) in the __pycache__ directory.
  2. If the bytecode file exists and is up to date (i.e., the source file has not been modified since the bytecode was generated), Python uses the bytecode file for execution, bypassing the compilation step.
  3. If the bytecode file does not exist or is outdated, Python compiles the source file into bytecode and stores it in the __pycache__ directory for future use.

GIL

The Global Interpreter Lock (GIL) in Python is a mutex that protects access to Python objects, preventing multiple native threads from executing Python bytecode at the same time. This means that even in a multithreaded Python program, only one thread can execute Python code at a time.

The GIL exists because:

  • Python’s memory management (especially reference counting) is not thread-safe. so our GC wil not able to works better
  • It simplifies memory management and prevents race conditions.
  • Many core libraries (such as CPython’s built-in types) are not designed to be thread-safe.
  1. Single-threaded Performance: The GIL does not affect single-threaded Python programs.
  2. Multithreading Limitation: Since only one thread executes Python code at a time, CPU-bound tasks (e.g., numerical computations) do not benefit from multithreading.

IMPORTANT

In standard CPython, threads are concurrent but not truly parallel for CPU-bound tasks. This is because of the Global Interpreter Lock (GIL), which ensures that only one thread executes Python bytecode at a time. However, for I/O-bound tasks (like network calls or file operations), threads can improve responsiveness by overlapping waiting periods.

Async IO (build in python 3.4)

asyncio module provides infrastructure to write single-threaded concurrent code using coroutines, multiplexing I/O access over sockets and other resources, running network clients and servers, and other related primitives.

  1. Coroutines (async/await): Coroutines are special functions that can pause execution at await expressions and then resume where they left off. They are defined using async def syntax and can be paused and resumed asynchronously.

  2. Event Loop: The event loop is the central component of asyncio. It manages and schedules coroutines, IO operations, and callbacks. The event loop continuously checks for events such as IO operations, callbacks, and scheduled tasks, and executes them in an asynchronous manner.

  3. Tasks: Tasks are used to schedule coroutines for execution on the event loop. A task wraps a coroutine, allowing it to be scheduled and managed by the event loop.

  4. Event Loop Policies: Event loop policies allow you to customize the event loop used by asyncio. This can be useful for integrating asyncio with other event loops or frameworks.

Event loop

It continuously runs, listening for events (like I/O operations) and dispatching tasks when they’re ready.

  • asyncio.get_event_loop() returns the current event loop associated with the running thread.

ByteCode

Why is if not mylist Faster?

  • if not mylist: Directly checks truthiness in one step.
  • if len(mylist) == 0: Calls len() + compares, adding overhead.

Since Python treats empty sequences as False, the first approach avoids a function call, making it almost 2x faster.

The reason why if not mylist is nearly twice as fast as if len(mylist) == 0 lies in how CPython executes these expressions internally. Let’s break it down step by step.

Bytecode for if not mylist

  2           0 LOAD_FAST                0 (mylist)
              2 POP_JUMP_IF_FALSE         8
  3           4 LOAD_CONST                0 (None)
              6 RETURN_VALUE
  • LOAD_FAST 0 (mylist): Load the list reference.
  • POP_JUMP_IF_FALSE 8: Check if the list is empty and jump accordingly.

Bytecode for if len(mylist) == 0

  6           0 LOAD_GLOBAL              0 (len)
              2 LOAD_FAST                0 (mylist)
              4 CALL_FUNCTION            1
              6 LOAD_CONST               1 (0)
              8 COMPARE_OP               2 (==)
             10 POP_JUMP_IF_FALSE        16
  7          12 LOAD_CONST               0 (None)
             14 RETURN_VALUE
  • LOAD_GLOBAL 0 (len): Load the len() function.
  • CALL_FUNCTION 1: Call len() with one argument (mylist).
  • LOAD_CONST 1 (0): Load the constant 0.
  • COMPARE_OP 2 (==): Compare len(mylist) with 0.

This involves an extra function call (len()), which adds overhead.

When we create a class, Python automatically adds a __dict__ attribute to each instance. This dictionary holds all instance attributes, making attribute access dynamic and flexible but memory-intensive for large numbers of objects.

When we define __slots__ in a class, Python doesn’t create the __dict__ for instances. Instead, memory is preallocated for only the specified attributes, reducing memory usage and making attribute access faster.

Python Execution

  • Python is a programming language.
  • CPython is the default implementation, written mainly in C.
  • Python code is compiled into bytecode.
  • Python Virtual Machine (PVM) executes bytecode.
  • .pyc files store cached bytecode.

Flow: .py → Compiler → Bytecode → PVM → CPU

Why Python Is Slow

  • Dynamic typing.
  • Object management overhead.
  • Reference counting.
  • Bytecode interpretation.
  • Function calls and memory allocation.

Solution: Native code, JIT, NumPy, Cython.

GIL (Global Interpreter Lock)

  • A lock in traditional CPython.
  • Only one thread executes Python bytecode at a time per interpreter.
  • Prevents unsafe concurrent access to interpreter internals.
  • Limits CPU-bound threading.
  • Threads are useful for I/O-bound tasks.
  • The main reason is we have GC which increament the reference counter if we allow multithread we might get issue

  • Parallelism: Tasks execute simultaneously.
  • I/O-bound: Waiting for network, files or database.
  • CPU-bound: Performing calculations.

Free-threaded Python:

  • Optional GIL-disabled build.
  • Allows parallel execution using threads.
  • Uses additional synchronization mechanisms.
  • May have performance overhead.
  • Some C extensions may not support it.

JIT (Just-In-Time Compilation)

  • Compiles frequently executed code into machine code at runtime.
  • Optimizes repeated execution paths.
  • Reduces interpreter overhead.
  • Useful for long-running workloads.
