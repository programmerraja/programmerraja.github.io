1. Architecture & psql

In nutshell → one postmaster process listens on 5432 and forks a new process for every connection. All processes talk through shared memory.

flowchart TB
    App1[App instance 1] --> PGB
    App2[App instance 2] --> PGB
    PGB["PgBouncer (optional pooler)"] --> PM

    subgraph Server["PostgreSQL server"]
        PM["Postmaster :5432"] -- "fork per connection" --> B1[Backend 1]
        PM -- fork --> B2[Backend 2]
        PM -- fork --> B3[Backend 3]

        subgraph SHM["Shared memory"]
            SB["shared_buffers (8KB pages cache)"]
            WB[WAL buffers]
            LT[Lock table]
        end

        B1 <--> SHM
        B2 <--> SHM
        B3 <--> SHM

        subgraph BG["Background processes"]
            CP[Checkpointer]
            BW[Background writer]
            WW[WAL writer]
            AV[Autovacuum workers]
            WS[WAL sender]
        end

        BG <--> SHM
    end

    SB -- "dirty pages, later" --> DF[("Data files base/")]
    WB -- "on COMMIT, fsync" --> WAL[("pg_wal/")]
    WS -- "WAL stream" --> R[(Replica)]
  • Postmaster → parent process, accepts connection and forks a backend.
  • Backend process → one per client. Parses, plans and executes your queries.
  • Background processes → checkpointer, background writer, WAL writer, autovacuum launcher + workers, WAL sender (replication).
  • Shared memory → shared_buffers (page cache), WAL buffers, lock table. This is how the processes share state.

Why process and not thread

  • Fault tolerance: one backend crash won’t corrupt others’ memory (in threads it would).
  • Cost: each backend is a few MB of RAM + fork cost → default max_connections = 100. That’s why people put PgBouncer in front (see section 9).

Everything is append → even an UPDATE writes a new row version, old one becomes dead and vacuum cleans it later (section 6).

How a query runs

flowchart LR
    Q[SQL text] --> P["Parser (syntax check, parse tree)"]
    P --> RW["Rewriter (expand views, rules)"]
    RW --> PL["Planner (uses pg_stats, picks cheapest plan)"]
    PL --> EX["Executor (runs plan nodes, reads pages)"]

Aggregation

CTE & recursive CTE

CTE = named subquery, makes long queries readable. Since PG12 the planner inlines it (no perf penalty) unless we write MATERIALIZED.

A common table expression (CTE) allows us to create a temporary result set within a query

Here’s the basic syntax for creating a common table expression:

WITH cte_name (column1, column2, ...) AS (
    -- CTE query
    SELECT ...
)
-- Main query using the CTE
SELECT ...
FROM cte_name;
  • WITH clause: Introduce the common table expression (CTE). It is followed by the name of the CTE and a list of column names in parentheses. The column list is optional and is only necessary if you want to explicitly define the columns for the CTE.
  • CTE name: Specify the name of the CTE. The CTE name exists within the scope of the query. Ensure that the CTE name is unique within the query.
  • Column List (optional): Specify the list of column names within the parentheses after the CTE name. If not specified, the columns implicitly inherit the column names from SELECT statement inside the CTE.

Window functions

Aggregate without collapsing rows. OVER (PARTITION BY ... ORDER BY ...)

row_number → 1,2,3 | rank → 1,1,3 | dense_rank → 1,1,2

Upsert & RETURNING

The upsert allows you to update an existing row or insert a new one if it doesn’t exist.

PostgreSQL does not have the UPSERT statement but it supports the upsert operation via the INSERT...ON CONFLICT statement.

NULL traps

  • NULL = NULL → NULL (not true). Use IS NULL or IS DISTINCT FROM.
  • NOT IN (subquery) where subquery has a NULL → returns zero rows. Use NOT EXISTS.
  • count(*) counts rows, count(col) skips NULLs.
  • sum of no rows → NULL, not 0. Use coalesce(sum(amount), 0).

How a row is stored under the hood

 one row (tuple) inside an 8KB page
┌───────────────────────┬──────────────┬───────────────────────────────────┐
│ header 23 bytes       │ null bitmap  │ column data, each column aligned  │
│ xmin xmax ctid flags  │ 1 bit / col  │ id | created_at | name | payload  │
└───────────────────────┴──────────────┴───────────────────────────────────┘
  header + bitmap padded to 24 bytes (multiple of 8)
  • NULL costs no data bytes, only 1 bit in the null bitmap (bitmap exists only when the row has a NULL).
  • Fixed size types (int, bigint, timestamptz, uuid…) stored inline and must start at an aligned address → padding bytes get added between columns.
  • Variable length types (text, numeric, jsonb, arrays, bytea) = “varlena” (variable length). Their size changes per row, so Postgres stores the length in front of the value: 1 byte length header if value ≤ 126 bytes, 4 byte header otherwise. 'hello' in a text column = 1 + 5 = 6 bytes.
  • Every row also pays the 24 byte header → a table of tiny rows (2 ints) is mostly header. 100M rows × 24B = 2.4GB just headers.

Column tetris (alignment & padding)

the order we write columns in CREATE TABLE is the order they sit on disk. A bad order wastes empty bytes in every row.

Why there are empty bytes at all

  • The CPU reads memory in chunks of 8 bytes. An 8 byte number is fastest (and on some CPUs only possible) to read when it starts at an address divisible by 8. This rule is called alignment.
  • Postgres keeps a row on disk in exactly the same byte layout it uses in memory, so a page can be read from disk and used directly with no conversion. So the disk layout follows the CPU’s alignment rules too.
  • Rule per type (the “Aligned to” column in the table above): bigint / timestamptz must start at an offset divisible by 8, int / date by 4, smallint by 2. boolean, uuid and short text can start anywhere.
  • If the previous column ends at a position that breaks this rule, Postgres fills the gap with empty padding bytes.

Same 6 columns, two orders:

Byte by byte (each cell = 1 byte, . = padding)

order A: 48 data bytes, 17 of them wasted
 0       4       8              16      24             32  34      40             48
 [id    ][. . . ][created_at    ][p . . . . . . ][amount_cents  ][st][. . .][user_id      ]
  4 B     4 pad    8 B             1B   7 pad       8 B            2B  6 pad   8 B
          ▲ created_at must start at 8          ▲ amount must start at 24  ▲ user_id at 40

order B: 31 data bytes, 0 wasted
 0              8              16             24      28  30 31
 [created_at    ][amount_cents  ][user_id      ][id    ][st][p]
  8 B             8 B             8 B            4 B     2B  1B
  • In order A, id ends at byte 4, but created_at must start at a multiple of 8 → 4 empty bytes. Same thing after is_paid (7 empty) and after status_code (6 empty).
  • In order B every column ends exactly where the next one is allowed to start → no gaps. Big ones first means each later (smaller) column always lands on an allowed position.

Measured on PG18:

Smaller rows = more rows per 8KB page = fewer pages to read, more of the table fits in RAM, smaller backups.

Ordering rule for CREATE TABLE

  1. 8 byte: bigint, timestamptz, double precision (and uuid, 16 bytes but no alignment, fits anywhere)
  2. 4 byte: integer, date, real
  3. 2 byte: smallint
  4. 1 byte: boolean
  5. variable length last: text, numeric, jsonb, arrays → their size differs per row, so a fixed column placed after them lands on a different offset in each row and may need padding in some rows
  6. Columns that are often NULL near the end. A NULL takes no bytes, so it doesn’t matter much, but it keeps the fixed columns at fixed positions

When it matters → tables with tens of millions of rows (events, logs, orders). For a 10k row settings table, write columns in whatever order reads best. Postgres can’t reorder columns later (ALTER TABLE always adds at the end), so changing it = create a new table and copy data → decide at create time.

TOAST (The Oversized-Attribute Storage Technique) → a row has to fit inside one 8KB page, and Postgres wants at least 4 rows per page. So when a row goes over ~2KB, Postgres shrinks it:

flowchart LR
    R["Row > ~2KB"] --> C["Compress big values (pglz / lz4)"]
    C --> Q{"Still > ~2KB?"}
    Q -- no --> IN[Stored inline, compressed]
    Q -- yes --> OUT["Move value to pg_toast table<br/>in ~2KB chunks"]
    OUT --> P["Row keeps an 18 byte pointer"]

  • Reading a TOASTed column = extra lookups + decompress. SELECT * on a table with big jsonb/text pulls all of it → select only the columns needed.

  • Columns not touched by the query are not de-TOASTed → big values in their own column are cheap if we don’t select them.

IDs

  • serial = old shortcut that creates a sequence + default. Identity is the SQL standard version and ALWAYS refuses manual ids unless OVERRIDING SYSTEM VALUE.
  • Mistake → int primary key on a fast growing table (events, logs). At 2,147,483,647 every insert fails. Fixing it = int -> bigint rewrite of the biggest table in the DB. bigint costs 4 extra bytes, always use it.
  • Mistake → importing rows with explicit ids into a serial column. Sequence doesn’t move → next normal insert gets duplicate key. Fix:

  • Sequences never roll back (rollback, failed insert, cache) → ids have gaps. Never use them as “gapless invoice numbers” → keep a counter row and UPDATE ... RETURNING it inside the transaction.

  • Sequential ids in URLs leak how many users/orders we have and allow scraping /users/1, /users/2... → internal bigint PK + a public uuid column.

UUID

  • Stored as 16 bytes. As text it’s 37 bytes, slower to compare, and 'ABC...' vs 'abc...' become different values.
  • UUID v4 is random → each insert lands on a random B-tree page → page splits, index bloat, the index stops fitting in cache as the table grows.
  • UUID v7 starts with a timestamp → inserts append to the end of the index like bigint. uuidv7() is built in from PG18, before that generate v7 in the app. gen_random_uuid() = v4.

Text

  • text, varchar, varchar(n) = same storage, same speed. varchar(n) only adds a length check.
  • Raising a varchar(n) limit is instant, lowering it scans/rewrites. When the length rule matters use text + CHECK (length(name) <= 100) → easy to change later.
  • char(n) pads with spaces up to n → wasted bytes and weird comparisons. Never.
  • Case-insensitive unique email → CREATE UNIQUE INDEX ON users (lower(email)); and always query with lower(email). Or the citext extension.
  • Gotcha → text sort order and text indexes depend on the OS collation library (glibc / ICU). An OS upgrade that changes collation rules (glibc 2.28 did) can silently break index order → wrong query results. REINDEX text indexes after such upgrades. Postgres logs a collation version mismatch warning.

Numbers & money

  • numeric → exact decimal, stored as base-10000 digits, slower math than ints. Right for money, rates, quantities.
  • float / real → approximate:
  • money type → formatting depends on server locale (lc_monetary), no currency stored. Avoid.
  • bigint cents (amount_cents = 1999) → fast and exact, common in payment systems. Always store currency next to it.
  • numeric(5,2) rejects 1000.00 with an error instead of silently rounding → good, it catches bugs.

Time

  • timestamptz doesn’t store a timezone. It converts input to UTC, stores 8 bytes, and shows it in the session TimeZone. Same size as timestamp.
  • Mistake → timestamp (no tz) with app servers in different zones, or across DST changes → ambiguous values that can’t be fixed later.
  • Need the user’s original zone (“meeting at 9am Asia/Kolkata”)? Store the zone name in a separate text column.
  • now() = transaction start time (same value for every row in the transaction). clock_timestamp() = real current time.
  • date for birthdays / business days, interval for durations (now() - interval '7 days').
  • Mistake → WHERE date(created_at) = '2026-10-28' → function on column, index on created_at not used. Use a range:
  • Mistake → BETWEEN '2026-10-01' AND '2026-10-31' on timestamptz misses everything after 00:00 on the 31st. Use >= start AND < next_start.

Boolean, status & enum

  • Mistake → nullable boolean = 3 states (true / false / unknown). Use boolean NOT NULL DEFAULT false.
  • Status column, 3 options:
OptionGoodBad
text + CHECK (status IN (...))easy to change (drop + add constraint)text bytes on every row
enum4 bytes, sorts by declared orderADD VALUE is easy, removing a value is not possible without recreating the type
lookup table + FKcan hold label, sort order, flagsone more join

Other types worth knowing

  • inet / cidr → IPs with operators: WHERE ip << '10.0.0.0/8'

  • Domain → reusable type + rule: CREATE DOMAIN email AS text CHECK (VALUE ~ '^[^@\s]+@[^@\s]+$');

  • Generated column → total_cents bigint GENERATED ALWAYS AS (qty * price_cents) STORED. PG18 adds VIRTUAL (computed on read, no disk) and makes it the default.

  • bytea → small binary only. Files go to S3, DB stores the key. Big blobs bloat backups, replication and cache.

JSON vs JSONB

  • json → stores the text as-is (keeps whitespace, duplicate keys, key order), parses on every read.
  • jsonb → parsed into a binary format on write. Can be indexed. Slightly slower write. Use jsonb.

Under the hood of jsonb

  • On write: whitespace dropped, duplicate keys → last one wins, key order is not kept.
  • Big documents (> ~2KB) get TOASTed (compressed, moved out of the row).
  • Updating one key rewrites the whole document → new row version + new TOAST value. A counter inside a 50KB jsonb updated every second = 50KB written every second, plus WAL.
  • Planner has no statistics inside jsonb → it guesses row counts for payload->>'country' = 'IN' → bad plans. An expression index fixes it (ANALYZE collects stats for indexed expressions), or promote the key to a real column.

Indexes on jsonb

Mistakes

  • Comparing numbers as text → payload->>'price' > '10' is a text compare, '9' > '10' is true. Cast: (payload->>'price')::numeric > 10.
  • JSON null vs SQL NULL → '{"a": null}'::jsonb -> 'a' is a jsonb null (not SQL NULL). ->> returns SQL NULL. IS NULL checks behave differently on each.
  • Using jsonb to skip schema design → every reader must handle missing / renamed / wrongly typed keys forever. Good fit: external API payloads, user settings, sparse optional attributes. Bad fit: core fields we filter, join or sort on.
  • jsonb can still have rules: CHECK (payload ? 'type' AND jsonb_typeof(payload->'amount') = 'number')

Arrays

  • Stored as one value (header + dimensions + elements). Changing one element rewrites the whole array. Big arrays get TOASTed.
  • Index starts at 1, not 0: tags[1].
  • No FK on elements, no per-element uniqueness → if elements are other entities (user ids, product ids) use a join table.
  • Good fit: small lists read with the row (tags, scores, feature flags).

4. Schema design & safe migrations

In nutshell → the schema is the set of rules our data can never break. App code changes every week, data lives for years and is written by many apps, scripts and people. Push the rules into the DB.

erDiagram
    users ||--o{ orders : places
    orders ||--o{ order_tags : has
    tags ||--o{ order_tags : labels
    users {
        bigint id PK
        uuid public_id UK
        timestamptz created_at
        text email UK
        text plan
    }
    orders {
        bigint id PK
        bigint user_id FK
        bigint amount_cents
        text status
        jsonb ship_address
    }
    order_tags {
        bigint order_id PK, FK
        bigint tag_id PK, FK
    }
    tags {
        bigint id PK
        text name UK
    }

Why each choice

  • NOT NULL on almost everything → NULL means “unknown”, not “empty”. Every nullable column is a 3-state value every query has to think about.
  • Constraint per business rule (amount_cents > 0, allowed statuses) → a bug in any app, script or manual UPDATE gets rejected instead of stored.
  • ON DELETE RESTRICT on orders → deleting a user who has orders fails instead of silently deleting money history.
  • ON DELETE CASCADE on order_tags → rows that only exist because of the parent go with it.
  • ship_address copied into the order → the order must show where it was shipped even after the user edits the profile. That’s a fact of the order, not duplication.
  • Column order: 8 byte columns first, then text/jsonb (column tetris, section 3).

Naming

  • Unquoted names are folded to lowercase: CREATE TABLE Users creates users.
  • Mistake → quoted mixed case names ("CreatedAt", often from ORMs). Now every raw query must write "CreatedAt" with quotes forever. Use snake_case, and map names in the ORM.
  • user and order are reserved words → name tables users, orders.
  • Name constraints and indexes ourselves (users_email_uq) → error messages and migrations become readable.

Schemas (namespaces)

  • Cluster → database → schema → table. Default schema is public. search_path decides which schema an unqualified name means.
  • Split modules or keep extensions apart: CREATE SCHEMA billing; CREATE TABLE billing.invoices (...).
  • Since PG15 normal users can’t create objects in public by default → grant explicitly.

Keys

  • Surrogate key (bigint identity) as PK + UNIQUE on the natural key (email, sku).
  • Mistake → natural key as PK (email, phone, username). They change → the change has to cascade into every FK in every table.
  • Composite PK only for join tables ((order_id, tag_id)).

Normalization

In nutshell → each fact is stored in one place.

  • 1NF → one value per column (no "pg,redis,kafka" text lists).
  • 2NF / 3NF → every non-key column depends on the key, the whole key, and nothing else (the user’s name lives in users, not copied into every order).
  • Denormalize only for a measured read problem, and keep one source of truth: counter column updated in the same transaction, or a materialized view for reports

Constraints i

  • UNIQUE allows many NULLs (NULL ≠ NULL). Two users with phone = NULL is fine, usually what we want. For “only one NULL” → UNIQUE NULLS NOT DISTINCT (PG15+).
  • Partial unique index → rule for a subset of rows:
  • CHECK only sees the current row. Rules across rows → UNIQUE / EXCLUDE constraint, or a trigger.
  • Deferrable → checked at COMMIT instead of per statement. Needed for swapping unique positions or circular FKs:
  • FK actions: NO ACTION / RESTRICT (default, safe), CASCADE (only for owned children), SET NULL.
  • Gotcha → CASCADE on a big tree: one DELETE FROM users can delete millions of rows across tables in one transaction, holding locks the whole time.
  • Gotcha → Postgres does not auto-create an index on the FK column (orders.user_id). Without it, joins are slow and every delete/update on users does a seq scan on orders to check for children. Always index FK columns.

Common modeling mistakes

  • Soft delete everywhere (deleted_at) → every query must remember WHERE deleted_at IS NULL, and a deleted user still blocks the email from signing up again. Fix: partial unique index ON users (lower(email)) WHERE deleted_at IS NULL, a view with only live rows, or move deleted rows to an archive table.

  • Polymorphic association (commentable_type = 'post', commentable_id = 7) → no FK possible, orphans pile up. Fix: one nullable FK per parent + rule that exactly one is set:

  • EAV tables (entity_id, attribute, value text) → every read is N self joins, no types, no constraints. Use a jsonb column.
  • Comma separated lists in text → can’t index, join or validate. Use an array or a join table.
  • Stored derived values without a rule (total column next to line items) → drift apart. Use a generated column or compute it.
  • Multi-tenant tables without tenant_id on child tables → can’t enforce isolation or use RLS. Put tenant_id on every table and first in composite indexes (tenant_id, created_at).
  • One hot row everyone updates (global counter, single settings row) → all writers queue on that row lock. Shard the counter (n rows, sum on read) or count async.
  • Files in the DB → table, backups and replicas grow by GBs. S3 + key.

What ALTER TABLE does under the hood

A table’s definition lives in catalog tables (pg_class = tables, pg_attribute = columns, pg_constraint, pg_index). Some changes only edit the catalog (instant). Others rewrite every row into a new file (slow, needs 2× disk, locked the whole time).

ChangeCost
ADD COLUMN nullable, or with a non-volatile default ('free', now())catalog only, instant
ADD COLUMN with a volatile default (gen_random_uuid(), clock_timestamp())full rewrite
DROP COLUMNcatalog only. Space comes back only as rows get rewritten. Dropped columns still count toward the 1600 column limit
RENAME COLUMN / RENAME TABLEcatalog only, but breaks every app still using the old name
ALTER TYPE varchar(50) -> varchar(100) or -> textcatalog only
ALTER TYPE int -> bigint, text -> intfull rewrite + rebuild every index
SET NOT NULLfull scan (skipped if a validated CHECK (col IS NOT NULL) exists)
ADD CHECK / ADD FOREIGN KEYfull scan (use NOT VALID + VALIDATE)
CREATE INDEXblocks writes for the whole build (use CONCURRENTLY)

Even the instant ones need a short ACCESS EXCLUSIVE lock → lock queue problem below.

Safe migrations on live big tables

Most ALTER TABLE takes an ACCESS EXCLUSIVE lock → blocks even SELECT. Worse, if it waits behind a long query, every query after it also waits (lock queue).

sequenceDiagram
    participant R as Report query (60s)
    participant T as users table
    participant M as ALTER TABLE
    participant A as App SELECTs
    R->>T: ACCESS SHARE (running)
    M->>T: wants ACCESS EXCLUSIVE
    Note over M,T: waits for report to finish
    A->>T: SELECT
    Note over A,T: queued BEHIND the ALTER -> app is down for 60s
    R-->>T: done
    M-->>T: runs, releases
    A-->>T: finally runs

So:

Backfill in batches → one UPDATE on 50M rows = one huge transaction: 50M new row versions, locks held for minutes, vacuum blocked, replicas lag. Small batches instead:

int → bigint on a big table without a long lock:

  1. ALTER TABLE events ADD COLUMN id_new bigint; (instant)
  2. Trigger copies id into id_new for new/updated rows
  3. Backfill old rows in batches
  4. CREATE UNIQUE INDEX CONCURRENTLY on id_new
  5. One short transaction: drop old PK, rename columns, add PK USING INDEX, move the sequence

Every step except the last runs while the app keeps writing.

Rename/drop a column the app uses → expand and contract, each step is its own deploy:

flowchart LR
    A[Add new column] --> B[App writes both] --> C[Backfill old rows in batches] --> D[App reads new] --> E[Stop writing old] --> F[Drop old column]

5. Functions, views & triggers

  • View → saved query, no data stored.
  • Materialized view → stores the result. REFRESH MATERIALIZED VIEW CONCURRENTLY mv; (needs a unique index, doesn’t block reads).

Procedural languages

Write logic (loops, IF, variables) inside the DB.

  • PL/pgSQL → default and most used. Loops, IF, variables, exception handling.
  • PL/Python (plpython3u) → use Python libraries inside the DB. Untrusted (u), only superuser can create functions.
  • Function vs procedure → function is called in SELECT and can’t COMMIT. Procedure is CALLed and can commit inside (batch jobs).
  • Volatility → IMMUTABLE (same input = same output forever), STABLE (same within a query, e.g. now()), VOLATILE (default, e.g. random()). Planner uses this, and expression indexes need IMMUTABLE.

Triggers

Gotcha → hidden logic nobody sees in app code, and slows bulk writes. Keep them for data integrity / audit, not business logic.

LISTEN/NOTIFY → trigger calls pg_notify('orders', id::text), app LISTEN orders and reacts. Not durable: if the listener is down the message is lost (same as Redis pub/sub in Redis).

Connection pooling

Every connection is a process (section 1) → opening one per request is slow and 1000 connections kill the DB.

  • App-side pool (node-postgres pool, HikariCP, SQLAlchemy pool) + PgBouncer in between when many app instances.
  • More connections ≠ faster. A small pool (around cores × 2–4) usually beats a big one.
  • PgBouncer transaction mode gotcha → the server connection changes between transactions, so session state breaks: SET (use SET LOCAL), session advisory locks, LISTEN. Prepared statements need PgBouncer 1.21+ (max_prepared_statements).

Parameter placeholders

Never build SQL by string concat with user input → SQL injection. With placeholders the driver sends the query and the values separately, so input is always data, never code.

  • Postgres native: $1, $2 (node-postgres uses this)
  • psycopg: positional %s, named %(name)s
  • Cast when needed: WHERE id = %(id)s::integer
  • Lists / dicts map to arrays / jsonb

ORMs

  • N+1 → load 100 users, then 1 query per user for orders = 101 queries. Use the ORM’s eager loading (include, joinedload) or one JOIN.
  • Turn on SQL logging in dev and read what the ORM generates.
  • Raw SQL for reports, bulk updates, window functions. Notes on Prisma in Prisma.

Transactions from the app

  • Keep them short. No HTTP calls inside a transaction (payment API slow → locks held → pile up).
  • Retry on 40001 (serialization failure) and 40P01 (deadlock).
  • Set statement_timeout per app role so one bad query can’t run forever: ALTER ROLE api SET statement_timeout = '5s';

Bulk load & export

  • COPY is the fastest way in/out. \copy in psql does it from the client machine.
  • Inserting from app → multi-row VALUES (...), (...), ... in batches of ~1000, not one insert per row.

11. Tricks that replace extra stack

Why this section exists: when an app needs search, tags, maps, a job queue or a cache, the usual answer is to add a new service: Elasticsearch, Redis, a geo service. Each one is another system to host, back up, monitor, and keep in sync with the main database. PostgreSQL already does many of these jobs. Weigh team size and operations cost before adding a tool: one database you know well is often cheaper than five you run badly.

Each trick below has the problem it solves, the idea in plain words, and an example. The examples use made-up tables (articles, providers, events…), so swap in your own names.

Terms used in this section

  • Index: a sorted side structure that lets Postgres find rows without reading the whole table (section 7). Like the index at the back of a book.
  • GIN and GiST: two index types. GIN is good at “does this contain X” (words in a document, items in an array, keys in JSON). GiST is good at shapes and locations.
  • tsvector / tsquery: a document turned into a list of stemmed words, and a search turned into words to match (section 10).
  • @>: “left side contains right side”, for arrays and JSONB. @@: “this text matches this search”.
  • CTE (WITH ...): a named sub-query. Several steps can run inside one statement.
  • LATERAL: a sub-query that can read columns from the row to its left, so it runs once per row.
  • Partial index: an index that only covers rows matching a WHERE.
  • Partition: one big table split into smaller child tables, usually by date.
  • Transaction: a group of statements that either all happen or none do (section 6).

Search: prototype, index, then rank

The problem: WHERE title LIKE '%queue%' cannot use a normal index, so Postgres reads every row and gets slower as the table grows. It also misses word forms: queues does not match queue. Full-text search splits text into words, drops small words like the and a, and reduces each word to its root (running becomes run). So queue also finds queued and queuing.

The idea: start with the simplest query, make it fast with an index, and add weights and ranking only when results need sorting. Each step adds more to maintain, so stop at the step your app needs.

Build it in 3 steps, each one only when you need it.

  1. Ad-hoc → tsvector (words of the doc) @@ tsquery (the search). No schema change, good for trying ideas.
  2. Expression GIN index → index the same expression, queries get fast, still no new column. The query must use the exact same expression or the index is ignored.
  3. Stored tsvector column → needed for weights (title counts more than body) and ranking with ts_rank / ts_rank_cd (cover density, rewards words close together).

What the 3 steps do

  1. Ad-hoc: to_tsvector turns the title and body into words on the fly. websearch_to_tsquery turns what the user typed into a search, understanding quotes and -word for “exclude”. @@ is true when the document matches. Nothing is indexed, so it is slow on a big table, but it is good for testing a search idea.
  2. Expression index: the GIN index stores the result of that exact expression. Postgres uses it only when the query repeats the same expression, so copy it exactly.
  3. Stored column: GENERATED ALWAYS AS ... STORED keeps the tsvector in its own column and updates it on every insert and update. setweight(..., 'A') marks title words as more important than body words ('B'). ts_rank_cd gives each row a score, and ORDER BY rank DESC puts the best match first.

More on full-text in section 10.

Tags and attributes: arrays + JSONB

The problem: a job has several tags, or optional details like “floor number” or “pet allowed” that differ per job. Splitting these into extra tables means a join for every filter. Postgres can store them on the row: an array for a list, JSONB for named values that vary.

The idea: ask “does this row contain these tags or values?” with @>. A GIN index makes that fast.

Both are filtered with the containment operator @> (“left contains right”) and both use a GIN index.

  • text[] → list of tags/topics. tags @> ARRAY['a','b'] = has all of these.
  • jsonb → flexible key-value data (extracted metadata, optional fields). attrs @> '{"floor": 2}' = has this key/value.
  • jsonb_path_ops is a smaller, faster GIN for @> only (no ? key-exists operator).

What the queries do

  • tags @> ARRAY['plumbing','urgent'] returns jobs that have both tags. A job with only one of them is not returned.
  • attrs @> '{"floor": 2}' returns jobs where floor is 2. Jobs without a floor key are simply not returned, with no error.
  • DEFAULT '{}' gives every row an empty array or object, so you never have to handle NULL.
  • jsonb_path_ops builds a smaller, faster index, but only for @>. Use the default GIN if you also need ? (“has key X”).

Geo with PostGIS

The problem: “which providers cover this address?” or “who is within 5 km?” can be done in app code by loading rows and doing the distance maths yourself. That is slow, easy to get wrong, and pulls far more rows than needed.

The idea: PostGIS adds geo types (points and polygons) and functions for them. You store each provider’s service area as a polygon and let the database answer the question. A GiST index lets it skip areas that are nowhere near.

Terms

  • Point: one location, like a customer’s GPS pin.
  • Polygon: an outline on a map, like a service area.
  • SRID 4326: the coordinate system of normal GPS (latitude and longitude in degrees).

Real geo types and functions instead of lat/lon math in app code. Store points and polygons, ask spatial questions, index with GiST.

  • ST_Within(a, b) → a is fully inside b (point in service area).
  • ST_Intersects(a, b) → shapes touch or overlap.
  • ST_DWithin(a, b, metres) → proximity (“within 5 km”). Cast to geography to get metres.
  • ST_MakePoint(lon, lat) → longitude first. 4326 = normal GPS coordinates (WGS 84).

What the queries do

  • ST_MakePoint(80.27, 13.08) creates a point. The order is longitude first, then latitude, which often trips people up. ST_SetSRID(..., 4326) tells Postgres these are GPS coordinates.
  • ST_Within(point, area) is true when the point lies inside the polygon. Use it for “who serves this address?”
  • ST_DWithin(a, b, 5000) is true when the two are within 5000 metres. The ::geography cast makes the distance real metres. Without it the distance is in degrees.

Combine search + tags + geo in one query

The problem: a search like “plumber near me for a leak” often goes to three places: a search engine for the text, a tag filter, and a geo service for distance. The app then merges the results, which is slow and fragile.

The idea: text, tags and location are all columns on the same table. One WHERE with three conditions checks all three, and Postgres picks an index for each part.

Because all of it is plain SQL, one statement filters text, tags and location together and the planner picks the indexes. No app-side merging of 3 services. Assume providers also has search tsvector and tags text[] from above.

What the query does

  • Every line after WHERE is a filter. A row must pass all of them.
  • The text match uses the search index, the tag check uses a GIN index, and the location check uses a GiST index.
  • ts_rank only sorts the results so the best text match comes first. Tags and location just filter rows.
  • The coordinates are typed in directly for clarity. In a real app, pass them in as parameters ($1, $2, see section 9).

Flexible schema: JSONB + CHECK + FILTER

The problem: a survey changes every month. Adding a column for each new question needs a migration (section 4), and most rows end up NULL in most columns.

The idea: store the answers in one jsonb column. New questions need no migration. The trade-off: Postgres does not know which keys exist, so you enforce the shape yourself with CHECK.

Terms

  • JSONB: JSON stored in a binary form that is fast to query (section 3).
  • FILTER (WHERE ...): counts only the rows that match a condition, inside a single SELECT. It replaces SUM(CASE WHEN ... THEN 1 ELSE 0 END).

Forms and surveys change every month, adding a column each time hurts. Store the answers as jsonb.

  • CHECK + jsonb_typeof → JSONB has no schema, so enforce the shape yourself (object, number, string…). A missing key gives NULL and passes the check, so combine with ? or NOT NULL if the key is required.
  • count(*) FILTER (WHERE ...) → many conditional counts in one pass over the table, no CASE or several queries.

What the code does

  • The first CHECK says the whole answer must be a JSON object {...}, not a list or a plain value.
  • The second says if age is present, it must be a number. A missing age gives NULL, and a NULL check passes, so age is optional. To make it required, add CHECK (answers ? 'age').
  • The bad insert fails because "old" is text, not a number. Nothing is saved.
  • -> returns JSON, ->> returns text. Cast with ::int before comparing numbers.
  • The final SELECT returns three counts in one pass: all rows, rows that answered yes to recommend, and rows aged 30 or more.

Partial unique index: one active row, keep history

The problem: a member can have only one active subscription, but cancelled ones should stay for history. A normal UNIQUE (member_id) checks every row, so it blocks a new subscription even after the old one is cancelled.

The idea: a unique index with a WHERE only compares the rows that match that WHERE. Active rows must be unique, and cancelled rows are ignored by that rule.

“One active subscription per member” but old cancelled ones stay for history. A normal UNIQUE can’t do that. A unique index with a WHERE only checks the rows that match it. See also partial indexes in section 7.

What the statements do

  1. The first insert works, since member 1 has no active row yet.
  2. The second insert fails with a duplicate key error, because member 1 already has an active row.
  3. The update moves that row to cancelled. It stays in the table, so the history is kept.
  4. The insert works again, because member 1 no longer has an active row.

Writable CTE: query + update + insert in one statement

The problem: billing the unbilled commissions from the app takes several round trips: read the commissions, mark them billed, create the invoice, then create one line per commission. If the app crashes halfway, the data is half-billed.

The idea: a WITH block can contain UPDATE, INSERT or DELETE. RETURNING hands back the rows those statements touched, and later steps can use them. The whole thing is one statement, so it all happens or none of it does.

Terms

  • CTE (WITH name AS (...)): a named step you can reuse later in the same statement.
  • RETURNING: gives back the rows that an INSERT, UPDATE or DELETE changed.

UPDATE / INSERT / DELETE ... RETURNING can sit inside a WITH, and the next step reads what the previous one returned. All steps are one statement → atomic, one round trip, no app code holding rows in between.

What the statement does

  1. due marks every unbilled commission for agent 7 as invoiced, and returns the id and amount of each one.
  2. inv creates one invoice with the total of those amounts. HAVING count(*) > 0 skips the invoice when there was nothing to bill.
  3. The final INSERT creates one invoice_lines row per commission, linking each one to the new invoice.

LATERAL: kill the N+1

The problem: you want each tenant’s latest invoice. The app loads all tenants, then runs one query per tenant. With 500 tenants that is 501 queries. This is the N+1 problem, and the cost is mostly round trips to the database.

The idea: LATERAL lets a sub-query read the current row’s values, so Postgres can run it once per tenant inside a single query.

“Latest invoice per tenant” in the app = 1 query for tenants + 1 per tenant. LATERAL runs the subquery once per left row and it can see that row’s columns, so top-N per row is one query. LEFT JOIN LATERAL ... ON true keeps tenants with no invoice. Back it with an index on (tenant_id, created_at DESC).

What the query does

  • For each tenant t, the sub-query finds that tenant’s invoices, newest first, and keeps one (LIMIT 1).
  • LEFT JOIN ... ON true means “always keep the tenant”. A tenant with no invoices still appears, with NULL in invoice_id and total. A plain JOIN would drop it.
  • The index on (tenant_id, created_at DESC) lets Postgres jump straight to each tenant’s newest invoice.

Task queue: SKIP LOCKED + partial index (+ ctid)

The problem: background jobs (send an email, process a payment event) need a queue. Redis or a message broker works, but it is one more service to run. With several workers reading the same queue, two of them can also grab the same job.

The idea: the events table is the queue. A worker picks the next pending row with FOR UPDATE SKIP LOCKED. FOR UPDATE locks the row so nobody else changes it, and SKIP LOCKED skips rows another worker already locked instead of waiting. Each worker gets a different event.

Terms

  • Row lock: while one transaction holds it, other transactions that want the same row wait, or skip it with SKIP LOCKED.
  • Pending: a row with processed_at IS NULL. The worker sets processed_at when it finishes.

A table is the queue, no Redis. Each worker locks a few pending rows, rows already locked by another worker are skipped, so two workers never take the same event. Crash before COMMIT → rollback → lock released → the event is pending again (retry for free). Partial index on pending rows keeps the scan small while the table grows with processed history.

ctid is the physical row address (page, row), like a shelf number in a warehouse. Every UPDATE moves the row to a new shelf, so the number changes. Inside the same transaction, while the row is locked, it is a cheap way to point back at the row you just picked. Internal detail → it changes after an UPDATE or VACUUM FULL, so never store it outside the transaction. Using id is always safe.

What happens, step by step

  1. BEGIN starts a transaction. The lock lasts until COMMIT or ROLLBACK.
  2. The SELECT picks the oldest pending event and locks it. Other workers skip it and take the next one.
  3. The worker does the job. Keep it short, because the row stays locked the whole time (no slow HTTP calls, see section 9).
  4. The UPDATE marks the event done, and COMMIT releases the lock.
  5. If the worker crashes before COMMIT, the database rolls back, the lock is released, and the event is still pending for another worker. That is an automatic retry.

The partial index only holds pending rows, so finding the next one stays fast even after millions of processed events.

SKIP LOCKED basics also in section 6.

Time series: pack, align, roll up, fill

The problem: meter and sensor data arrives often and at irregular times. One row per reading wastes space, readings don’t line up on clean times, and reports need totals per day or per hour. The four tricks below each fix one of these.

One row per reading (a meter every 30 min = 48 rows/day/meter) wastes space because every row has a 24 byte header (section 3). Four tricks together:

1. Pack readings into an array → one row per meter per day. Unpack with unnest ... WITH ORDINALITY when you need rows. Good for narrow points that are written once and read together.

What it does

  • Each row holds one meter’s 48 half-hour readings for one day, in an array. That is 1 row per day instead of 48, so less overhead and fewer index entries.
  • CHECK (cardinality(kwh) = 48) rejects a day with the wrong number of readings.
  • unnest ... WITH ORDINALITY turns the array back into rows. n is the slot number (1 to 48), and day + (n - 1) * 30 minutes turns it into a timestamp.
  • Trade-off: changing one reading rewrites the whole day’s row. Use this for data written once and read together.

2. Align irregular timestamps with generate_series → readings arrive at 00:03, 00:41… Build the clean grid and pick the last reading at or before each grid point.

What it does

  • generate_series makes a clean list of times, every 30 minutes across the day: 00:00, 00:30, 01:00, and so on. The real readings don’t have to arrive at those times.
  • For each clean time g, the LATERAL sub-query picks the latest real reading at or before g. This is the same trick as in the LATERAL section.
  • LEFT JOIN ... ON true keeps a clean time even when no reading exists yet, giving NULL. The next trick fills those gaps.

3. Rollups and deltas with window functions → date_trunc buckets time, lag looks at the previous row. A meter shows a running total, usage per interval = this reading minus the previous one.

What it does

  • lag(reading) gives the previous reading (ordered by time). Subtracting it gives the usage since the last reading. The first row has no previous row, so its usage is NULL.
  • This assumes reading is a running total, like a meter dial. If your readings already are the usage per interval, skip the subtraction.
  • date_trunc('day', ts) rounds every timestamp down to midnight, so GROUP BY day gives one total per day.

4. Fill gaps with a custom aggregate + window → Postgres has no built-in “last non-null”. Make one (state = last non-null value seen). As a window function it carries values forward. Run it twice, ORDER BY ts (previous known) and ORDER BY ts DESC (next known), and you can interpolate between them.

What it does, step by step

  1. keep_last is the rule for the custom aggregate: keep the new value if it is not NULL, otherwise keep the old one. coalesce(v, state) does that.
  2. CREATE AGGREGATE last_known wraps that rule so it can be used as a window function. Postgres has no built-in version.
  3. OVER (ORDER BY ts) walks forward. prev_v is the last known value so far and prev_ts is the time it was recorded. The CASE makes sure prev_ts is the time of a real reading, not of the current row.
  4. ORDER BY ts DESC walks backward and gives next_v and next_ts, the next known value and its time.
  5. For a missing row, the value is a straight line between the two known points. The fraction of the way from prev_ts to next_ts decides how far to go from prev_v to next_v. Rows that already have a value keep it, thanks to coalesce.
  6. nullif(..., 0) turns a zero gap into NULL instead of a division error. At the start or end of the series there is only one known side, so the result stays NULL.

Use only last_known(value) OVER (ORDER BY ts) if you just want to carry the last value forward.

Q&A extras

  • Old data cleanup (TTL) → partition by time, then drop a whole partition. DETACH + DROP is instant, DELETE of millions of rows is slow and leaves bloat (section 3 of Internals). pg_partman automates creating and dropping partitions (section 10).
  • ORM in the way → use raw SQL, or let Postgres build the JSON so the app just forwards it.

What it does

  • Partition: the big events table is split by month into child tables. A query that filters by date only reads the months it needs.
  • Cleanup (TTL, “time to live”): DETACH turns a month into a standalone table without moving data, and DROP removes it at once. Deleting millions of rows with DELETE is slow and leaves dead rows behind (section 3 of Internals). Detach first if you want to archive the month instead.
  • json_agg builds one JSON array inside SQL, so the app can pass it straight to the browser without mapping each row to an object by hand.

Optimization

PostgreSQL planner cost constants are relative weights used by the query optimizer to estimate execution costs, anchored to seq_page_cost = 1.0.

Key Constants

  • seq_page_cost (1.0): Sequential disk page read.
  • random_page_cost (4.0): Random disk page read (lower to 1.1–1.5 for SSDs/NVMe).
  • cpu_tuple_cost (0.01): Processing one row.
  • cpu_index_tuple_cost (0.005): Processing one index entry.
  • cpu_operator_cost (0.0025): Evaluating one operator or function.
  • parallel_setup_cost (1000.0): Spawning parallel workers.
  • parallel_tuple_cost (0.1): Passing one row from a parallel worker to the leader.
  • effective_cache_size (4GB): Hint for total OS + shared_buffers cache (set to ~50–75% of RAM).

PostgreSQL 18 introduced native Asynchronous I/O (AIO), allowing query backends to submit multiple disk read requests simultaneously and continue CPU processing while waiting for storage—delivering up to 2–3x faster cold reads on cloud block storage and NVMe drives

Before PostgreSQL 18, all actual data reads into PostgreSQL’s shared_buffers were strictly synchronous and blocking:

  • One blocking step at a time. When a query backend needed a page not in memory, it called a blocking read() (or preadv() in PG 17) syscall. The backend process paused completely and sat idle until the kernel fetched the data from storage.
  • Reliance on OS readahead guesswork. To hide that blocking cost, PostgreSQL relied on the operating system’s page cache to guess what blocks to prefetch next, or issued advisory hints via posix_fadvise(POSIX_FADV_WILLNEED) (used in bitmap heap scans, VACUUM, and PG 17’s read streams
